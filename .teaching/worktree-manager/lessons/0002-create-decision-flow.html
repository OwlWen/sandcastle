第 2 课 — create() 的决策流程

📁 L291 – L428 📏 138 行 🎯 能画出完整的决策树并解释每个分支

create() 是整个 WorktreeManager.ts 最复杂的函数。它处理的不只是"创建 worktree"——它要同时应对碰撞检测、分支存在性、复用策略、以及降级路径。这节课用一张决策流程图 + 逐步注解把它拆干净。

1. 函数签名——先看入口和出口

export const create = (
  repoDir: string,
  opts?: {
    branch?: string;       // 指定分支名（branch 策略）
    baseBranch?: string;   // 新建分支时的起点（默认 HEAD）
    name?: string;         // 给临时分支加一个可读名字
  },
): Effect.Effect<
  WorktreeInfo,                          // 成功：{ path, branch }
  WorktreeError | WorktreeTimeoutError,  // 失败：两种错误
  FileSystem.FileSystem                  // 依赖：文件系统服务
>
读 Effect 签名的技巧：Effect.Effect<A, E, R> 三个泛型参数分别是：
A = 成功值，E = 可能的错误，R = 运行时需要的环境/依赖。
这里要求调用方提供 FileSystem.FileSystem 服务——因为函数需要创建目录。

3. 逐步注解走读

1 确保目录存在 (L304-308)

fs.makeDirectory(worktreesDir, { recursive: true }) —— 幂等创建 .sandcastle/worktrees/。

注意错误被 mapError 转换为 WorktreeError——这是 Effect 中统一错误类型的标准手法。

2 计算 branch 和 worktreeName (L310-327)

这里有个容易忽略的细节——branch 和 worktreeName 的命名规则不同：

branch（git 分支名）

sandcastle/my-run/20260830-151642-a1b2c3

用 / 分隔，因为 git 分支名支持斜杠（看起来像目录结构）

worktreeName（目录名）

sandcastle-my-run-20260830-151642-a1b2c3

用 - 分隔，因为目录名不宜包含斜杠

当 opts.branch 存在时：worktreeName = branch.replace(/\//g, "-")——简单地把斜杠换成连字符。

3 核心分岔：有 branch vs 无 branch (L331 / L385)

这是整个函数最重要的分岔点。理解它需要回忆两种 branch strategy：

有 opts.branch（branch 策略）

用户指定了分支名 → 可能复用已有 worktree → 需要碰撞检测

进入 复杂路径（L331-384，54 行）

无 opts.branch（merge-to-head）

生成唯一的临时分支名 → 碰撞概率极低 → 直接创建

进入 简单路径（L385-413，29 行）

4 碰撞检测——findCollidingWorktree 的双重匹配 (L335-336) 
const existing = yield* listWorktrees(repoDir);
const collision = findCollidingWorktree(existing, branch, worktreePath);

为什么要 两重匹配（先 branch、再 path）？

因为 mid-rebase 状态下，worktree 的 HEAD 是 detached 的，git worktree list --porcelain 输出中 branch 字段为 null——按 branch 匹配会漏掉它。fallback 到路径匹配可以兜住这个 case。

实际场景：Agent 在 worktree 中执行 git rebase，中途 pause 了。此时分支名对不上，但目录还在 → 路径匹配命中 → 安全复用。
5 碰撞后的三种命运 (L337-361)
条件结果行号
碰撞 + managed + dirty console.warn + 原样复用 L341-344
碰撞 + managed + clean fastForwardFromOrigin() + 复用 L345-346
碰撞 + 不是 managed ❌ 抛出详细错误信息 L352-361

"不是 managed" 意味着分支被 checkout 在主工作树或用户自己创建的外部 worktree 中——Sandcastle 不能动这些，只能报错。

6 新建 worktree 的"先试后创"降级 (L363-384) 
yield* execGit(
  [...NO_CONFIG_LOCK_FLAGS, "worktree", "add", worktreePath, branch],
  repoDir,
).pipe(
  Effect.catchAll((e) => {
    if (e.message.includes("invalid reference")) {
      // 分支不存在 → 降级为 -b 创建新分支
      return execGit([
        ...NO_CONFIG_LOCK_FLAGS, "worktree", "add", "-b",
        branch, worktreePath, opts?.baseBranch ?? "HEAD",
      ], repoDir);
    }
    return Effect.fail(e);  // 其他错误原样抛出
  }),
);

这是一个 optimistic try → fallback 模式：

  1. 先假设分支已存在，尝试 git worktree add path branch（checkout 现有分支）
  2. 如果 git 报 "invalid reference"（分支不存在），降级为 -b 创建新分支
  3. 降级时使用 baseBranch ?? "HEAD" 作为起点
为什么不先 git branch --list 检查再决定？这是 TOCTOU 的经典避免——在检查和操作之间分支状态可能变化。直接尝试 + 按错误降级更安全。
7 临时分支的简单路径 (L385-413)

当没有 opts.branch 时，分支名是唯一的（带时间戳+随机后缀），所以直接 -b 创建新分支 + worktree。碰撞只可能在极端情况下发生（并发 + 随机碰撞），错误信息提示用户等待或换名字。

8 全局超时守卫 (L417-428) 
.pipe(
  withTimeout(WORKTREE_TIMEOUT_MS, () =>  // 30 秒
    new WorktreeTimeoutError({ ... })
  ),
);

整个 create() 被 30 秒超时包裹。这防止 git 子进程卡死（比如等待 lock 文件释放）时无限挂起整个 run。

4. fastForwardFromOrigin 深入

第 5 步中 clean worktree 走的 fastForwardFromOrigin() 本身也有 4 个决策分支：

检查条件结果行号
HEAD 指向 HEAD 不在目标分支上（detached / 其他分支） 跳过刷新，日志说明原因 L221-232
fetch git fetch origin branch 失败（无网络 / 无 origin / 分支不在远端） 跳过刷新，非致命 L234-244
merge git merge --ff-only origin/branch 失败（diverged） 保持原样，未推送提交不丢 L250-260
对比 SHA merge 前后 HEAD SHA 是否变化 变了 → "Fast-forwarded"；没变 → "Reusing" L262-274
注意返回类型：Effect.Effect<void, never>——错误通道是 never，意味着这个函数永远不会失败。所有错误都在内部用 Effect.either / Effect.orElseSucceed 吞掉了。这是 ADR 0003 "非致命"原则的直接体现。

5. 边缘场景集

以下 5 个边缘场景在测试中都有覆盖，理解它们能帮助你在脑中"跑"完整个决策树：

🔸 Mid-rebase 的 clean worktree 不应被快进

Agent 在 worktree 中 git rebase --exec false HEAD~2 中途暂停。HEAD 是 detached 的，working tree 是 clean 的。

行为：fastForwardFromOrigin() 检查 symbolic-ref HEAD → 发现不在目标分支 → 跳过刷新。Rebase 状态完好保留。

代码: L221-232 · 测试: test L518-578

🔸 没有 origin remote 时 fetch 失败不阻塞

仓库没配 origin（纯本地 repo）。

行为：Effect.either(execGit(["fetch", ...])) 返回 Left → 打印日志 → 原样复用。绝不抛错。

代码: L234-244 · 测试: test L461-483

🔸 有未推送提交但 origin 没动（strictly ahead）

worktree 有本地 commit，origin 还在旧位置。merge --ff-only 成功（no-op），commit 保留。

行为：merge 成功但 HEAD SHA 没变 → 打印 "Reusing existing worktree"。

代码: L266-273 · 测试: test L485-516

🔸 分支存在于外部 worktree（非 sandcastle 管理）

用户在主工作树中 checkout 了 main 分支，然后调用 create(repoDir, { branch: "main" })。

行为：isManagedWorktreePath() 返回 false → 抛出详细错误信息，解释 git 的单分支互斥限制和解决办法。

代码: L352-361 · 测试: test L648-659

🔸 baseBranch 在分支已存在时被忽略

调用 create(repoDir, { branch: "existing-branch", baseBranch: "some-sha" })，但 existing-branch 已存在。

行为：第一次 git worktree add path branch 就成功了（分支已存在），不走 -b 降级，所以 baseBranch 根本不被使用。

代码: L363-364 · 测试: test L328-359

🧪 检验理解

调用 create(repoDir, { branch: "feat/x" }) 时，如果 "feat/x" 分支不存在，git 会先报什么错误，然后代码如何降级？

  • 报 "already exists"，降级为删除旧目录后重建
  • 报 "invalid reference"，降级为 -b 从 HEAD 新建分支
  • 报 "not a valid branch"，降级为临时分支名重试
  • 不报错，git worktree add 会自动创建缺失分支

🧪 检验理解

为什么 findCollidingWorktree() 需要 两重匹配（branch + path），而不是只匹配 branch？

  • Windows 上 branch 名可能包含反斜杠导致匹配失败
  • git 有时不返回 branch 字段所以需要备用匹配
  • mid-rebase 时 HEAD 是 detached 的，branch 为 null
  • 两个不同分支可能生成相同的 worktreeName 目录

🧪 检验理解

fastForwardFromOrigin() 的返回类型中，错误通道为什么是 never？

  • 因为 git 操作在这个上下文中不可能失败
  • 因为 Effect-TS 要求 void 返回的函数不能有错误
  • 所有错误都被 either/orElseSucceed 内部消化了
  • 因为外层 create() 已经有超时兜底了
