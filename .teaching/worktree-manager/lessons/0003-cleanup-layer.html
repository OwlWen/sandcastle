第 3 课 — 清理层、跨平台陷阱与完整生命周期

📁 L430 – L539 + 辅助函数 📏 ~110 行 🎯 理解清理层的三个函数 + Windows 路径标准化 + 模块完整生命周期

前两节课我们搞定了 create() 的全部路径。这节课把剩下的清理层一次讲完，再从调用者视角看 worktree 的完整生命周期——这样你就能从头到尾读懂整个模块了。

1. hasUncommittedChanges — 最简单的函数（L434-439）

export const hasUncommittedChanges = (
  worktreePath: string,
): Effect.Effect<boolean, WorktreeError> =>
  execGit(["status", "--porcelain"], worktreePath).pipe(
    Effect.map((output) => output.trim().length > 0),
  );

6 行代码，零决策分支。但它是整个复用逻辑的判定器——create() 和 cleanupWorktree() 都依赖它来决定 dirty vs clean。

porcelain 的含义：git status --porcelain 输出的是机器可解析的格式（不受 locale 和终端宽度影响）。有输出 = 有变更，没输出 = clean。
它覆盖三种变更：unstaged 修改、staged 暂存、untracked 新文件。但不包括已提交但未推送的 commit——这些不算 "dirty"（ADR 0003 的定义）。

2. remove — 路径反推的巧妙设计（L447-455）

export const remove = (
  worktreePath: string,
): Effect.Effect<void, WorktreeError> => {
  // Derive the main repo dir:
  // worktreePath = <repoDir>/.sandcastle/worktrees/<name>
  const repoDir = join(worktreePath, "..", "..", "..");
  return execGit(["worktree", "remove", "--force", worktreePath], repoDir).pipe(
    Effect.asVoid,
  );
};

9 行代码，但有一个隐含的契约：

前置条件：worktreePath 必须是 <repoDir>/.sandcastle/worktrees/<name> 格式。remove() 靠向上走三级目录来反推 repoDir——如果路径结构不对，git 命令的 cwd 就会指向错误的位置。

这就是为什么 create() 碰到"外部 worktree"碰撞时直接报错而不尝试复用——如果路径不在 .sandcastle/worktrees/ 下，remove() 就没法正确工作。

路径反推示例： worktreePath = /home/dev/myrepo/.sandcastle/worktrees/feature-x
join(worktreePath, "..", "..", "..") = /home/dev/myrepo ← repoDir

另一个值得注意的点：--force flag。这意味着即使 worktree 有未提交修改也照删——调用者（SandboxFactory.cleanupWorktree、interactive.ts）负责在调用前做 dirty 检查，remove() 本身不做保护。

3. pruneStale — 最微妙的函数（L461-538）

pruneStale() 做两件不同的清理，顺序很重要：

步骤做什么为什么
Step 1 (L472) git worktree prune 清理 git 知道但目录已不存在的残留元数据（.git/worktrees/<id>/）
Step 2 (L509-526) 扫描并删除孤儿目录 清理 目录还在但 git 已不认识的残留文件夹
为什么需要两步？
这两步处理的是对称的残留场景：
• 进程崩溃后 rm -rf 清理了目录 → git 元数据残留 → Step 1 解决
• git worktree remove 被中断，元数据已清理但目录还在 → Step 2 解决
两步一起保证无论哪种残留都能被清理。

Step 2 的逐行拆解

// L477-485: 读取 .sandcastle/worktrees/ 的目录列表
const entries: string[] | null = yield* fs.readDirectory(worktreesDir).pipe(
  Effect.map((es): string[] | null => es),
  Effect.catchSome((e) =>                       // ← 只捕获 NotFound
    e._tag === "SystemError" && e.reason === "NotFound"
      ? Option.some(Effect.succeed(null as string[] | null))
      : Option.none(),                           // ← 其他错误继续传播
  ),
  Effect.mapError((e) => new WorktreeError({ message: e.message })),
);

if (entries === null) return;  // 目录不存在 → 没什么要清理

注意 catchSome 的精确性——只吞 NotFound，权限错误等其他问题仍然会抛出。这比 catchAll 更安全。

// L489-495: 解析符号链接
const realWorktreesDir = yield* fs
  .realPath(worktreesDir)
  .pipe(Effect.catchAll(() => Effect.succeed(worktreesDir)));

这三行是为了修复一个真实 bug：

🐛 Issue #470 — 符号链接导致活跃 worktree 被误删

场景：用户把 .sandcastle 配成一个符号链接（指向外部存储）。

问题：fs.readDirectory() 返回的路径基于未解析的符号链接路径（/repo/.sandcastle/worktrees/x），但 git worktree list 返回的是 realpath 后的真实路径（/mnt/ext/.sandcastle/worktrees/x）。两边对不上 → 所有活跃 worktree 看起来都是"孤儿" → 全被删掉。

修复：先 realPath() 解析 worktreesDir，用解析后的路径拼接 entryPath，这样和 git 的输出就能匹配了。

// L498-507: 构建活跃 worktree 路径集合
const worktreeList = yield* execGit(["worktree", "list", "--porcelain"], repoDir);
const activeWorktreePaths = new Set(
  worktreeList
    .split("\n")
    .filter((line) => line.startsWith("worktree "))
    .map((line) => line.slice("worktree ".length).trim()),
);

这里直接解析 porcelain 输出而不复用 listWorktrees() 函数——因为 pruneStale 只需要路径，不需要 branch 信息。更简单，更少解析。

// L510-525: 扫描 + 删除孤儿
for (const entry of entries) {
  const entryPath = join(realWorktreesDir, entry);  // ← 用 realPath 后的路径
  const isDir = yield* fs.stat(entryPath).pipe(
    Effect.map((s) => s.type === "Directory"),
    Effect.catchAll(() => Effect.succeed(false)),   // stat 失败当作非目录
  );
  if (isDir && isOrphanedWorktreePath(entryPath, activeWorktreePaths)) {
    yield* fs.remove(entryPath, { recursive: true, force: true }).pipe(...);
  }
}

两个防御性细节：

  • stat 失败不抛出——可能是读取瞬间文件被删了（TOCTOU），降级为"不是目录"跳过
  • 只删目录不删文件——用户可能在 worktrees 目录下放了其他文件（虽然不推荐）

4. 跨平台路径标准化——那个你可能忽略的 normalizePath

整个模块有 4 个函数依赖 normalizePath——一个只有一行的函数：

const normalizePath = (p: string): string => p.replace(/\\/g, "/");

为什么需要它？因为 git 和 Node.js 在 Windows 上对路径分隔符的处理不一致：

Windows 上同一个路径的两种表示： git worktree list: C:/repo/.sandcastle/worktrees/feature-x (正斜杠)
node:path.join(): C:\repo\.sandcastle\worktrees\feature-x (反斜杠)

不标准化就直接比较？永远不匹配。结果：

受影响的函数不标准化时的后果
findCollidingWorktree() mid-rebase 路径 fallback 失败 → 碰撞检测漏网 → git 报奇怪错误
isManagedWorktreePath() managed worktree 被误判为 external → 本应复用的场景变成抛错
isOrphanedWorktreePath() 活跃 worktree 被误判为孤儿 → 数据丢失（bug #470 的 Windows 变体）
create() 返回值 L350: normalize(collision.path) 确保返回平台原生路径，不留 git 的正斜杠给下游
设计哲学：模块内部统一用正斜杠比较（通过 normalizePath），对外返回用 normalize()（Node.js 的原生函数，会转回平台分隔符）。进出口都有"翻译"。

5. 完整生命周期——从调用者视角

所有调用者都遵循同一个生命周期：

pruneStale() → create() → Agent 执行 → hasUncommitted? → remove() / 保留

以 SandboxFactory（最主要的调用者）为例，代码片段如下：

// 1. Prune → Create
const pruneAndCreate = () =>
  WorktreeManager.pruneStale(hostRepoDir).pipe(
    Effect.catchAll((e) => Effect.sync(() => {
      console.error("Warning: failed to prune:", e.message);
    })),                              // prune 失败不阻塞
    Effect.andThen(
      branch
        ? WorktreeManager.create(hostRepoDir, { branch, baseBranch })
        : WorktreeManager.create(hostRepoDir, { name }),
    ),
  );

// 2. Agent 执行...

// 3. Cleanup: check dirty → remove or preserve
const cleanupWorktree = (worktreePath, exit) =>
  WorktreeManager.hasUncommittedChanges(worktreePath).pipe(
    Effect.catchAll(() => Effect.succeed(false)),  // 检查失败当 clean
    Effect.flatMap((isDirty) => {
      if (isDirty) {
        // 保留 worktree，打印路径让用户检查
        return Effect.succeed(worktreePath);
      }
      // Clean → 安全删除
      return WorktreeManager.remove(worktreePath).pipe(
        Effect.map(() => undefined),
      );
    }),
  );

注意几个关键的容错设计：

失败点处理方式为什么
pruneStale 失败 catchAll → 打印警告继续 旧残留清理失败不应阻止新 worktree 的创建
hasUncommittedChanges 失败 catchAll → 当作 clean 检查失败时宁可删掉空 worktree，也不要残留占空间
remove 失败 不捕获，向上传播 如果连删目录都做不到，说明有严重问题，需要用户介入

🧪 检验理解

pruneStale() 的两步清理顺序能否颠倒——先扫描孤儿目录，再 git worktree prune？

  • 可以颠倒，两步完全独立互不影响
  • 不能颠倒，否则 git 会把已删目录的元数据当作 active
  • 不能颠倒，否则 Step 2 会删掉正在被 git 使用的锁文件
  • 可以颠倒，但颠倒后需要多调一次 git worktree prune

🧪 检验理解

为什么 remove() 不接受 repoDir 参数，而是从 worktreePath 反推？

  • 节省一个参数让函数签名更简洁方便调用
  • 调用方此时可能没有 repoDir 的上下文只有 worktreePath
  • 为了避免调用方传错 repoDir 导致删错仓库
  • 因为 git worktree remove 命令必须从子目录执行

🧪 检验理解

如果 .sandcastle 是一个符号链接，pruneStale() 不做 realPath() 会导致什么后果？

  • git worktree prune 会删除符号链接本身导致配置丢失
  • readDirectory 无法读取符号链接目标导致直接抛错退出
  • 所有活跃 worktree 看起来都是孤儿被全部误删导致数据丢失
  • 新建 worktree 会被创建到错误的路径导致 Agent 找不到
