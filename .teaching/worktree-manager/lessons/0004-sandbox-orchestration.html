第 4 课 — SandboxFactory 如何编排 Worktree

📁 src/SandboxFactory.ts 📏 692 行 🎯 理解 2×3 调度矩阵 + Effect 资源管理模式 + 错误附着机制

前三节课你读懂了 WorktreeManager.ts——它是一个"工具库"，纯粹负责 worktree 的 CRUD。这节课我们往上走一层，看 SandboxFactory 如何编排这些工具，把 worktree 生命周期嵌入到 sandbox 启停的完整流程中。

1. 两个新概念：Sandbox Provider × Branch Strategy

要读懂 SandboxFactory，必须先理解驱动它的两个维度：

Sandbox Provider（沙箱提供者）——Agent 运行在哪里？
三种变体，由 tag 字段区分：
  • "bind-mount" — Docker/Podman 容器，宿主机目录挂载进去（Agent 的写入直接反映在 host）
  • "isolated" — Daytona/E2B 等远端环境，有自己的文件系统（需 sync 才能把代码传回 host）
  • "none" — 不建容器，Agent 直接跑在宿主机上
Branch Strategy（分支策略）——Agent 的代码修改落在哪个分支？
三种变体，由 type 字段区分：
  • "head" — 直接写主工作目录，不创建 worktree
  • "merge-to-head" — 临时分支 → 合并回 HEAD → 删除临时分支（需要 worktree）
  • "branch" — 用户指定分支名（需要 worktree）

3. Effect 的 acquireUseRelease——资源管理的核心模式

每个绿色格子都用了同一个 Effect 模式：Effect.acquireUseRelease。如果你熟悉 try-finally 或 Go 的 defer，它就是 Effect 版的资源管理。

Effect.acquireUseRelease(
  acquire: pruneAndCreate(),        ──▶ 返回 worktreeInfo
  use:     (worktreeInfo) => { ... },  ──▶ 干活：copy、hook、sandbox、Agent
  release: (worktreeInfo, exit) =>     ──▶ 无论成功失败都执行
            cleanupWorktree(path, exit)
)
关键保证：即使 use 阶段抛出错误（Agent 崩溃、超时、用户取消），release 阶段一定会执行。这就是为什么 worktree 清理逻辑放在 release 而不是 use 的末尾——它是一种结构性保证，不可能被 early return 或异常跳过。

而且 SandboxFactory 用了嵌套的双层 acquireUseRelease：

外层 acquire/release: Worktree 生命周期
│
├─ acquire: pruneAndCreate()                  → worktreeInfo
│
├─ use: ─── copy → hook → ────────────────────────────────────┐
│                                                              │
│   内层 acquire/release: Sandbox 生命周期                   │
│   │                                                          │
│   ├─ acquire: startSandbox(worktreeInfo)     → handle       │
│   ├─ use:     makeEffect(info, sandbox)      → Agent 执行   │
│   └─ release: handle.close()                 → 关容器       │
│                                                              │
├─ release: cleanupWorktree(path, exit)        → 清理 worktree
│           ← 即使 copy 或 hook 失败也会执行

为什么是双层？注释写得很清楚（L590-593）：

"Worktree creation and sandbox start are nested so the worktree is always cleaned up (outer release) even when a later step — copying, hooks, or sandbox start — fails. The provider handle is closed by the inner release, which only runs once the handle exists."

如果只用一层：copy 失败 → sandbox handle 还没创建 → 无法 close → worktree 也不会被清理。双层解决了这个问题。

4. 四条路径的具体差异

现在让我们对比四条有 worktree 的路径（绿色格子）在 use 阶段的差异：

none + worktree L392-456 
pruneAndCreate()
  → copyToWorktree(...)        // 可选：复制文件到 worktree
  → runHostHooks(onWorktreeReady)  // 可选：host hook
  → startSandbox(none provider) // 无容器，直接在 host 跑
  → makeEffect(info, sandbox)   // Agent 执行
  → cleanupWorktree(path, exit) // release

最简单的 worktree 路径——没有容器、没有 mount、没有 sync。

isolated + worktree L466-522 
pruneAndCreate()
  → runHostHooks(onWorktreeReady)
  → startSandbox(isolated provider, copyPaths)  // 启远端环境 + 同步代码进去
  → makeEffect(info, sandbox)
  │   info.applyToHost = () => syncOut(...)   // ← 独有：Agent 执行后拉回变更
  → handle.close()
  → cleanupWorktree(path, exit)

关键差异：SandboxInfo.applyToHost 暴露了一个 syncOut() 函数，让调用方在 Agent 完成后把远端代码变更拉回 host worktree。

bind-mount + head L525-582 
// 无 worktree — 直接用 hostRepoDir
runHostHooks(onWorktreeReady, hostRepoDir)
  → resolveGitMounts(hostRepoDir/.git)   // 解析 .git 挂载
  → patchGitMountsForWindows(...)        // ADR-0006 Windows 修复
  → startSandbox(bind-mount, gitMounts)  // Docker + 目录挂载
  → makeEffect(info, sandbox)
  → handle.close()

没有 worktree 也就没有 cleanup。resolveGitMounts 解析 .git 是目录还是文件（worktree 的 .git 是文件，指向父仓库）。

bind-mount + worktree（最完整路径）L594-686 
pruneAndCreate()                          // outer acquire
  → copyToWorktree(...)                   // 复制额外文件
  → runHostHooks(onWorktreeReady)         // host hook
  → resolveGitMounts(hostRepoDir/.git)    // 解析 .git mount
  → patchGitMountsForWindows(...)         // Windows 兼容
  → startSandbox(bind-mount, gitMounts)   // inner acquire: Docker
  → makeEffect(info, sandbox)             // inner use: Agent 执行
  → handle.close()                        // inner release: 关容器
  → cleanupWorktree(path, exit)           // outer release: 清理 worktree

所有特性全开的"满配"路径。比 none+worktree 多了 mount 解析和 Windows 补丁。

5. cleanupWorktree——清理阶段的完整逻辑

// L203-226
const cleanupWorktree = (
  worktreePath: string,
  exit: Exit.Exit<unknown, unknown>,   // ← Effect 的退出信号
): Effect.Effect<string | undefined, WorktreeError> =>
  WorktreeManager.hasUncommittedChanges(worktreePath).pipe(
    Effect.catchAll(() => Effect.succeed(false)),  // 检查失败当 clean
    Effect.flatMap((isDirty) => {
      if (isDirty) {
        // 保留 worktree，打印路径和清理命令
        printWorktreePreservedMessage(worktreePath, ...);
        return Effect.succeed(worktreePath);
      }
      if (!Exit.isSuccess(exit)) {
        console.error("Worktree removed (no uncommitted changes)");
      }
      return WorktreeManager.remove(worktreePath).pipe(
        Effect.map(() => undefined),
      );
    }),
  );

决策逻辑很清晰：

dirty?exit 成功?结果
✅ dirty成功保留 + "Run succeeded but worktree has uncommitted changes"
✅ dirty失败保留 + "Worktree preserved at ..."
❌ clean成功静默删除（用户不需要知道）
❌ clean失败删除 + "Worktree removed (no uncommitted changes)"
设计意图：dirty 时保留是为了让用户能 cd 进去检查 Agent 遗留的修改。clean 时删除是为了不让 .sandcastle/worktrees/ 堆积垃圾。

6. attachPreservedPath——错误附着机制

这是一个容易被忽略但很精巧的设计（L232-252）：

const attachPreservedPath = <E>(
  path: string | undefined,
  e: E | SandboxError,
): E | SandboxError => {
  if (path !== undefined) {
    if (e instanceof AgentIdleTimeoutError) {
      return new AgentIdleTimeoutError({
        ...e, preservedWorktreePath: path,   // ← 附着到错误对象上
      });
    }
    if (e instanceof AgentError) {
      return new AgentError({
        ...e, preservedWorktreePath: path,
      });
    }
  }
  return e;
};

问题：cleanupWorktree 在 release 阶段执行，但错误是在 use 阶段抛出的——它们在时间线上是分开的。怎么把 release 阶段的"保留路径"信息传递给已经抛出的错误？

解法：用一个闭包变量 preservedWorktreePath（L588），在 release 阶段写入，在 .pipe(Effect.mapError(...)) 中读取并附着到错误对象上。

时间线:
  use 阶段 → Agent 抛出 AgentError ──────┐
  release 阶段 → cleanupWorktree ─────┐  │
                                      │  │
                preservedPath = "/..." │  │
                                      ▼  ▼
  .mapError((e) => attachPreservedPath(preservedPath, e))
                                         │
                                         ▼
  调用方拿到: AgentError { preservedWorktreePath: "/..." }

这样 run() 的调用方就能从错误对象中拿到保留的 worktree 路径，进行后续处理（比如在 CI 中上传 worktree 作为 artifact）。

7. resolveGitMounts——worktree 的 .git 特殊处理

bind-mount 提供者需要把 .git 挂载进容器。但 worktree 的 .git 不是目录，而是一个文件：

普通仓库：  .git/           ← 目录，直接挂载
Worktree：  .git            ← 文件，内容是 "gitdir: /repo/.git/worktrees/<name>"

resolveGitMounts()（L264-288）处理这个差异：

// 如果 .git 是目录 → 只挂一个
if (stat.type === "Directory") {
  return [{ hostPath: gitPath, sandboxPath: gitPath }];
}

// 如果 .git 是文件 → 解析 gitdir 指向，挂两个
const gitdirPath = match[1]!;  // e.g. /repo/.git/worktrees/feature-x
const parentGitDir = resolve(gitdirPath, "..", "..");  // /repo/.git
return [
  { hostPath: gitPath, sandboxPath: gitPath },       // .git 文件本身
  { hostPath: parentGitDir, sandboxPath: parentGitDir }, // 父 .git 目录
];
为什么要挂父 .git 目录？ 因为 worktree 的 .git 文件只是一个指针。git 操作（commit、log、push）实际读写的是父仓库的 .git/ 下的共享数据（objects、refs）。不挂父目录 → 容器内 git 命令全部报错。

🧪 检验理解

SandboxFactory 为什么用双层嵌套的 acquireUseRelease？

  • 为了让 worktree 和容器在两个并行的 fiber 中独立管理
  • 确保 copy/hook 失败时 worktree 仍被清理，即使容器还未创建
  • 外层管成功路径的清理而内层管失败路径的清理以区分逻辑
  • Effect-TS 要求每种资源类型都有独立的 acquire/release 对

🧪 检验理解

当 Agent 因超时失败且 worktree 有未提交修改时，调用方如何获知保留的 worktree 路径？

  • 通过 WithSandboxResult.preservedWorktreePath 成功返回值
  • 通过 AgentIdleTimeoutError.preservedWorktreePath 错误属性
  • 通过 console.error 输出的文本消息中解析路径字符串
  • 通过读取 .sandcastle/worktrees/ 目录列表推断路径

🧪 检验理解

为什么 isolated 提供者不支持 head 分支策略？

  • 因为 isolated 环境没有 git 所以无法操作分支
  • 因为 isolated 有独立文件系统，无法直接写入 host 的主工作目录
  • 因为 head 策略不创建 worktree 而 isolated 必须要 sync
  • 这只是当前的实现限制，未来版本会支持
